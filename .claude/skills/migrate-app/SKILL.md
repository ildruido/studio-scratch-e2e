# Migrate an existing app

For an app that already ships, set up before the harness had modules (AI, who is signed in, roadmap) or before it had a lock. Goal: the app runs on the current harness with the **same behaviour for its users**. The app keeps what it has: AI on, its sign-in mode (invite-only unless its profile says otherwise) and its own roadmap files. The harness never picks a feature for it; the modules just make the app's existing features explicit.

Run this **in the app's own Project**, never from app-studio. Between features is best: no feature branch should be open. If `inventory` stops you, tell the App Creator and stop; never work around it.

## Steps

1. **Look first (read-only).** Make sure `app-studio` is current (`git -C ../app-studio pull`) and that its newest release says `Live check: passed` (if it says pending, tell the App Creator and stop). Run `node ../app-studio/scripts/studio-sync.mjs inventory --app .` (the master script, so it works on an app whose own copy is old). It changes nothing. Read its **Custom AI**, **CI** and **modules** lines before planning (see steps 2 and 4). Also read, without changing them: the default branch and leftover branches, `.github/workflows/` against the pack starters it lists as differing, and the app's Project instructions as the coordinator reports them.
2. **Write the plan, and get the App Creator's OK.** Before any change, send the App Creator (through the coordinator) a short plan in plain product terms: what the app uses today (AI on, access model, storage), which modules get switched on, which of the app's own files differ and how each will be merged, the way back for each step, and anything the inventory flagged as a stop (below), and the **names of the CI jobs the `main` ruleset must require** (the app's own, as the inventory lists them: `CI gate` for apps from 0.7.0, `check` for older ones; the `CI gate` in `new-app` is for new apps). If the inventory warns that a workflow skips pull requests by file path (`paths` / `paths-ignore` on `pull_request`), the plan includes making it start on every PR, or a notes-only PR will wait forever on a required check that never runs. The App Creator approves it; without the OK, stop.
3. **Migrate on one branch** (`chore/migrate-harness`), one PR, so the way back is reverting that PR:
   - `node ../app-studio/scripts/studio-sync.mjs pull --app .` (part A of `harness-sync`). Heads-up for the plan and hand-over: `pull` may also forward the app's hooks to the user-level `~/.claude/settings.json` (a write outside the app repo); say so to the App Creator before you run it. If it says starter files are **held back**, that is expected: add the modules the inventory named in the same branch, `node .claude/studio/studio-sync.mjs pack add ai` (artifact-only app), or `pack add ai-web` on a web app (it adds `ai` too), plus `pack add user` when the inventory found `user()` calls. **Do not add `roadmap`** unless the app has none and the App Creator asks: an app with its own roadmap files keeps them as they are.
   - Merge by hand each file the inventory listed as **differ**, from `app-studio/packs/*/starter/…`, keeping the app's own behaviour, then `node .claude/studio/studio-sync.mjs ack`. Apply the **App action** lines in `CHANGELOG.md` for the versions skipped (0.8 to now), notably 0.14.0 (profile rows), 0.16.0 (platform files, `fakePlatform(fakeAi(...))` in tests) and 0.17.0 (sign-in mode).
   - Record in the App profile: `AI | on`, `AI plan` as it is today, `Access model | only invited people` (or what the app really does), and `Storage shape` as the app stores things. Keep the sign-in behaviour unchanged: with no `SIGN_IN_MODE` set the server means invite-only; setting it to `invite` in `render.yaml` and `.github/workflows/ci.yml` is optional and recommended, never `open` or `none` here.
   - `node .claude/studio/studio-sync.mjs health` must pass, then `npm run check` (and the server checks on a web app), then the app's browser tests.
4. **Custom AI: harness only.** If the inventory says **CUSTOM AI DESIGN found** (the app's own AI routes, a `sample()` that takes the app's own input, its own usage ledger), the `ai` / `ai-web` modules are not a drop-in: they replace platform and server files and break the app's AI tests. Offer the App Creator **harness only** in the plan: pull the harness files, record the App profile, add no AI module, leave the app's AI and platform code alone, and track the module swap as a separate decision (its own issue). Say what switching the modules on would break.
5. **Stop on a usage table under another name.** (If both `ai_usage` and the old table exist, the inventory says a copy is under way: check the data is in `ai_usage`.) If the inventory says the AI usage table is not `ai_usage`, do not add `ai-web`: the module would create an empty `ai_usage` and every user's monthly allowance would start from zero. Report it to the App Creator with the table's name and propose a safe copy as its own step. Never touch the app's live database from here.
6. **Open the PR** (ready for review, titled `chore(harness): migrate to studio vX.Y.Z`) with a hand-over: what changed, what the inventory found, **what wasn't verified** (typically the live site and real AI calls). Merge as the app's `CLAUDE.md` says.
7. **Prove it with one small follow-up PR** (a one-line docs change) that merges by itself. If auto-merge or the `main` ruleset isn't set up, say which of the one-time repo settings is missing (`node .claude/hooks/app-setup.mjs admin-checklist --repo <owner/repo> --checks <the app's job name>` prints the exact clicks) and put it on the Admin's checklist; never call the migration done before this PR has merged.
8. **Hand back to the coordinator**: the result, the inventory in one paragraph, what wasn't verified, and any Admin action (for example selecting the "app-studio apps" cloud environment when the start-up message doesn't say "Studio harness loaded"). Do not start the other app.

## Way back

Revert the migration PR: it restores the app's previous harness copy, files and profile in one step. Nothing outside the app's repo is touched, and the database is never changed by this skill (the module's `ai_001_usage.sql` changes nothing where `ai_usage` and `monthly_allowance` already exist, and runs only when the app is next deployed).
