# New app

`app-studio` is the master copy of the harness. A new app gets a pinned copy (`.claude/studio/lock.json`) and later pulls updates with the `harness-sync` skill, so fixes flow from `app-studio` to every app. Ideas flow back as issues (`harness-idea`), never as edits.

**Where this runs.** Best in a Claude Code Project on the "app-studio apps" cloud environment (app-studio `README.md`, "Start a new app"): the coordinator starts this skill in a thread and relays its questions. It also works in a cloud or local session with `app-studio` and the app repo side by side. The App Creator answers product questions only; everything else is decided here.

## Branches (read the file only when it applies)

- **No stack decided yet** (step 2), or the App Creator says "start building" on a discovery app: read `${CLAUDE_SKILL_DIR}/discovery.md` and follow it with the steps below.
- **A static content site** (the `static-site` pack alone, no `base`; also a discovery app that becomes one): read `${CLAUDE_SKILL_DIR}/static-site.md`; its steps replace the ones it names.

## Steps

1. **Check the setup.** List the repos beside `app-studio` in the start folder.
   - **No app repo yet:** agree a short kebab-case repo name with the App Creator (`<app>`) and a 2-3 letter id prefix. Ask the Admin (through the coordinator in a Project) to create one empty private repo with that name at github.com/new (Claude can't create repos), with the exact clicks. In a Project, ask the coordinator to add the repo to the Project and start a **new** thread that runs `new-app` again (a running thread can't see a repo added after it started), passing on the name and prefix. In a session, ask the App Creator to start a new session with both repos. Stop here.
   - **The repo is attached but empty** (no commits, so no `main` to branch from or open a PR against): start `main` yourself with one GitHub call, `create_or_update_file` on the repo with path `README.md`, content `# <App name>`, message `chore: start the repo` and no branch (GitHub creates its default branch, `main`, from it). Then `git fetch origin` and branch from `origin/main`. If the session offers to create `main` instead, accept that. Don't ask the App Creator.
   - **The repo already exists with content** (for example after a discovery or inception phase with its own docs, skills and `CLAUDE.md`): read what is there first. Nothing is deleted: `install` and `pack add` never overwrite a file, and the existing docs become the input of step 8.
   - **Not on the "app-studio apps" environment** (no "Studio harness loaded" message at start-up): carry on, and add "select the cloud environment" to the Admin's checklist in step 12.
2. **Pick the start.** Ask the App Creator first: is the tech stack decided? **Not yet** (the app is still being shaped, or is docs only): take the **discovery path** (`discovery.md`) and skip steps 4's `pack add`, 6, 7, 9's npm commands, 10's required checks and 11. **Decided**: ask the App Creator one product question: start as an artifact prototype (a private page in the Claude app, fastest to try), go straight to a web app (own sign-in and hosting), or build a **static content site** (pages and posts for everyone to read, no sign-in or server, free Cloudflare hosting). Default: artifact prototype. For an artifact or web app the app has a platform layer from day one, so the other build can come later without rewriting features; once a web version exists, the artifact build stays as a prototype with smoke tests only. `node .claude/hooks/app-setup.mjs pack-plan --target artifact|web|web+artifact|static-site --ai on|off --access invite|open|none|shared [--storage per-person] [--roadmap yes] --slug <repo> --title "<App name>"` turns the answers (here and in step 7) into the exact commands, so don't work them out by hand. The answer picks the stack packs: `artifact`, `web`, or `web artifact` for a web app that keeps a prototype (the first pack named decides what `npm run build` builds), or `static-site` **alone**: it replaces `base` and never goes with `web` or `artifact`, so a site starts clean with it and follows `static-site.md`.
3. **Branch.** Work in the app repo's folder beside `app-studio` (clone it there in a local session) on a branch (`chore/bootstrap`, or the session branch in a cloud session or Project thread).
4. **Install the harness and the packs:**
   - If `install` or `pack add` stops with "not live-checked yet", app-studio's newest release is still awaiting its studio-scratch check and nothing was changed: tell the App Creator and stop (never pass `--live-check`; only the studio-scratch check does).
   - `node ../app-studio/scripts/studio-sync.mjs install --app .` copies the skills, agents, hook script and sync script into `.claude/`, writes the lock, and adds `CLAUDE.md` and `.claude/settings.json` from the templates when they don't exist yet.
   - `node .claude/studio/studio-sync.mjs pack add <packs> --slug <repo> --title "<App name>"` adds the stack packs (and the `base` pack they require): the packs' docs under `.claude/packs/`, plus the starter files (build and test configs, CI workflow, platform layer, a seed page with unit and browser smoke tests, and for `web` the server, Dockerfile and preview config) and the npm scripts and dev dependencies. It never overwrites a file the repo already has.
   - `npm install` (and `npm install --prefix server` for `web`).
   - Optional `mirror` pack, for an app whose code must be public (open-source licences such as the GPL) while the project files stay private: add it now or later (`pack add mirror`); the setup is in `.claude/packs/mirror/RELEASE.md`.
5. **Fill the App profile** in `CLAUDE.md`. If the repo already had a `CLAUDE.md`, `install` kept it: merge the template (`app-studio/plugins/studio/templates/CLAUDE.md`) into it by hand, so the App profile and the shared sections are there, and keep the old rules that still apply after the build starts (a decision log, writing rules); drop phase rules that end now (for example "no production code"). Project skills the repo already has stay; rename one that clashes with a harness skill. Set rows with `node .claude/hooks/app-setup.mjs profile set "Field=value" ...` (never retype the table). Then fill in app name, id prefix, stack, user, repo, release and preview targets, capabilities, domain rules, stack notes, and the product paragraph. Read each pack's `STACK.md` and `RELEASE.md` once: the stack notes only add what is specific to this app. Don't edit the copied skills, agents or pack docs: anything app-specific belongs in the profile.
6. **Stack files.** The pack's starter files are now the app's own code. Check that CI still starts no run for Markdown-only and `.claude/`-only changes and skips the browser tests for a version bump (the starter workflow does).
7. **Seed the app.** The packs already seed it: `index.html`, `src/main.ts`, the platform layer, a unit test and a browser smoke test per target, so CI has something real to run. The seed assumes no feature: it makes no AI call. Add the feature modules the App profile calls for (`packs/README.md`, "Modules"): if the profile says the app uses AI, `node .claude/studio/studio-sync.mjs pack add ai` adds the AI status line and its tests, and for a `web` app `pack add ai-web` (which also adds `ai`) adds the server's AI endpoint, monthly allowance and usage ledger. A web app without AI has none of that. **Who can get in** follows the App profile's Access model (ask it now, as `prd-intake` "Features" does, if it isn't recorded yet; there is no default): for a `web` app set `SIGN_IN_MODE` in `render.yaml` and in `.github/workflows/ci.yml` (`invite` for only invited people, `open` for anyone who signs up, `none` for anyone with no login; the server refuses to start until it is set). Every access model with sign-in, and an artifact app with per-person documents, gets `pack add user` (who is using the page); a no-login app doesn't. If AI is on and anyone can get in, raise the AI public use decision then (`prd-intake` "Features", question 4). Ask the App Creator one process question: a prioritised Roadmap list (Now / Next / Later) kept honest by a check; recommended, and `node .claude/studio/studio-sync.mjs pack add roadmap` adds it. Without it the app has no Roadmap list and CI never asks for one. Replace the placeholder page only when the first backlog item is built.
8. **Requirements.** Run `prd-intake` with the App Creator's description, or with the documents the App Creator points to (a spec or PRD, a Google or Claude Doc, the repo's discovery docs such as an MVP and roadmap), to write `docs/PRD.md` and `docs/BACKLOG.md`. Start `CHANGELOG.md` with an empty `Unreleased` section.
9. **Verify.** `npm run check`, `npm run test:e2e` (the web target needs Postgres: the pack's `scripts/cloud-setup.sh` starts one in a cloud thread and sets `DATABASE_URL` and `TEST_DATABASE_URL`; if the thread has none, CI runs them), `node .claude/studio/studio-sync.mjs check` and `node .claude/studio/studio-sync.mjs health` (the commit hook runs it too and blocks commits until the App profile is filled in). Commit the lockfiles.
10. **Merge, and let PRs merge themselves from now on.** Push, open the PR (`chore: bootstrap harness`) ready for review (CLAUDE.md "Git workflow"). Once its checks have run (so their names exist on GitHub), **confirm `main` is the repo's default branch** (the PR's base branch, or `git remote show origin`: "HEAD branch"); if it isn't, the Admin's first click is switching it, because project threads start from the default branch and the ruleset targets it. Then ask the Admin, through the coordinator in a Project, for the one-time repo settings (default branch `main`; only squash merging, auto-merge and delete-head-branches on; a `main` ruleset requiring the checks, no up-to-date requirement), as exact clicks: `node .claude/hooks/app-setup.mjs admin-checklist --repo <owner/repo> [--checks health] [--default-branch <name>]` prints them, so pass that text on instead of retyping it. When the Admin says they're done, switch on auto-merge for this PR (`enable_pr_auto_merge`, `mergeMethod: SQUASH`): if it works, the setup is verified and GitHub merges the PR when it's green; if GitHub says the PR is already clean (its checks finished green before the clicks), merge it now ("Git workflow", step 3) and verify auto-merge on the next PR; any other error says what's missing, so tell the Admin which click. If the Admin can't do it now, merge with the fallback in "Git workflow" and put the clicks on the Admin's checklist (step 12). From the next thread on, the environment loads this app's own harness, hooks included.
11. **First release.** Run the `release` skill for v0.1.0; record the new release target URL in the App profile.
12. **Project setup.** In a Project, end with one report to the coordinator. `node .claude/hooks/app-setup.mjs project-report --name "<App name>" --repo <owner/repo> [--studio ../app-studio] [--goal "<sentence>"] [--checks health] [--default-branch <name>] [--env-missing] [--cloudflare]` prints all four parts below (the Admin's checklist only as far as the flags say); you write only the proposed outcome sentence and add anything the stack notes need. The report contains:
    - the Project instructions: `app-studio/plugins/studio/templates/project-instructions.md`, the part below the line, with `<App name>` and `<app repo>` filled in, for the coordinator to set as **Project instructions**;
    - the settings for the coordinator to apply: thread model Sonnet, thread effort medium, coordinator model Opus;
    - a proposed outcome for the Project's **What do you want to work on?** box (General settings): one or two sentences from the PRD's goal and first milestone, e.g. "Ship <App name> v1: <the core promise>, tested by the App Creator on <the release target>". The coordinator asks the App Creator to approve it, then sets it if it can; otherwise it goes on the App Creator's checklist;
    - The Admin's checklist, as exact clicks, of what only the Admin can do and isn't done yet: the repo settings from step 10 (including the default-branch switch, if `main` isn't the default) if auto-merge couldn't be verified, selecting the "app-studio apps" cloud environment only if this thread had no "Studio harness loaded" message at all, repository secrets or host settings the stack notes need, and anything else this setup couldn't finish. (Before the bootstrap is merged, only app-studio's skills load and the app's hooks don't run yet; that is expected, not something to fix.)
    In a session, give the App Creator the same three parts for the Project the app will use.
13. **Harness ideas.** If anything in the harness got in the way during setup, send it with `harness-idea`; don't fix `app-studio` from here.
14. **Tell the App Creator** the app link, the backlog's first Ready items, and the test script for v0.1.0.
